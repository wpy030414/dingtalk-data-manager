# PRD — 钉钉企业数据网关

## 产品目标
让本地 AI Agent（Claude Code、Codex CLI 等）能通过 MCP 协议**安全、只读地访问企业钉钉数据**——通讯录、考勤、宜搭表单/流程——而无需：
- 自己处理 OAuth / accessToken 生命周期
- 理解钉钉两代 API 的符号差异（OAPI 表单编码 vs 新 API JSON）
- 手工串联多步 API 调用（如「查手机号 → 拿 userId → 查考勤」）

## 用户与使用场景
- **目标用户**：企业管理员 / 技术负责人，通过 `.mcp.json` 将一个 Node.js 子进程接入 Claude Code 等 MCP 客户端。
- **典型场景**：
  1. 管理员问「东校中学2025级今天谁迟到了」→ Agent 自动：定位部门 → 取成员 ID → 批量查考勤 → 列出迟到的。
  2. 管理员问「上次去天津参赛那个申请，审批到谁了」→ Agent 自动：列宜搭应用 → 查字段定义 → 按「天津」模糊搜表单数据 → 查流程实例 → 拉审批记录。
  3. 管理员问「15256592124 这个手机号是谁」→ Agent 直接调 `get_user_by_mobile`。

## 核心问题
钉钉 API 对 Agent **不友好**：
1. **版本混乱**：同一个功能（通讯录）同时有 `oapi.dingtalk.com/topapi/...`（表单编码 POST）和 `api.dingtalk.com/v1.0/contact/...`（JSON POST），baseURL 和一级 path 都不同。不能共用一个 baseURL。
2. **搜索语义简陋**：部门/用户搜索是单 token 子串匹配，「东校中学2025级」直接搜返回 0 条——因为实际是三层部门 `东校 / 中学 / 2025级`。
3. **单用户接口**：考勤打卡接口只接受一个 `userid`，44 个人的部门要调 44 次。
4. **宜搭表单数据不可读**：返回的 key 是 `textField_mr4at0xc` 而非「外出事由」，必须另外拉字段定义做翻译。
5. **所有宜搭接口强制 userId**：必须是有该应用数据权限的用户，Agent 不该知道这个。

## 功能及其意义
| 功能 | 解决什么 | 为什么需要 |
|---|---|---|
| 统一 MCP Server | Agent 无需感知钉钉鉴权/版本差异 | 一个子进程，27 个工具，Agent 能理解 |
| 多接口串联 | 手机号→userId→用户详情，一步完成 | Agent 不该写多步流程 |
| 模糊部门名定位 `find_department` | 复合名搜索 0 命中的坑 | 钉钉原生不支持的，网关补 |
| 模糊人名+部门线索 `find_user` | 「东校的张老师」落地 | 部门花名册本地过滤，比全库搜人更准 |
| 考勤批量接口 | `getupdatedata` 只支持单用户 | 网关内部遍历 userIds，Agent 只需传数组 |
| 宜搭字段定义 | formData 的 key 是人看不懂的 fieldId | 必须先拉字段定义才能翻译 |
| 只读注解 | 客户端知道这 27 个工具不会改数据 | 减少确认弹窗，允许安全重试 |
| 服务器 instructions | Agent 连接时自动获得使用指南 | 不用翻外部文档 |

## 功能之间的关系
```
配置 .env.yml ──→ Token 管理 ──→ 各 Client ──→ Service ──→ Gateway ──→ MCP 工具 ──→ Agent
                                               │
                                         模糊查询算法
                                         (部门树缓存/最长匹配切词)
```

## 范围与非目标
- **范围内**：通讯录（13 工具）、考勤（5 工具）、宜搭（9 工具）的只读查询。
- **范围外**：
  - 写操作（创建/修改/删除）。
  - 钉钉消息、日历、文档、审批通过等。
  - Web UI、REST API、GraphQL。
  - 数据持久化缓存（Token 除外）。
